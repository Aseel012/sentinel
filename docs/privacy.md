# Privacy and security

Sentinel observes the local system and makes no telemetry or network requests. Explicit persistence services retain history in a local SQLite database. Ordinary `status` remains read-only. There are no dedicated collectors for keystrokes, document contents, browser history, or packet payloads.

Process command lines and journal messages can contain credentials, personal information, and application data. Command text is capped at 1024 characters. Journal fields and messages have explicit bounds; truncation and other transformations are represented in event warnings and collection quality. A shared regex helper mitigates common inline credential forms. It cannot guarantee that secrets will not be collected or persisted; quoted, multiline, encoded, and unfamiliar secret forms can escape it.

Journal collection is explicitly invoked through `JournalEventService`; it reads only what the current account can access and never elevates permissions. It stores selected event fields, per-event warnings, and the latest collection result. It does not retain raw journal JSON or subprocess diagnostic text. Existing database permissions restrict database files to the owner, but there is no encryption at rest.

Journal writes retain at most 10,000 event rows by default (configurable through the application service). The existing retention module also supports an explicit UTC cutoff. Deletion preserves the checkpoint, so retention does not replay old journal entries. SQLite may reuse freed pages without shrinking the database file; this is neither secure erasure nor an exact disk-byte quota. Collection-quality metadata describes the latest poll, not an unlimited audit log.

Incident evidence stores identifiers, timestamps, service identities, relationship types, bounded summaries, and quality limitations. It does not copy journal messages, process command lines, or executable paths. Service names, event cursors, process lifetime identities, and summaries can still reveal operational information. Incident retention is separate from source retention, and deleting source observations does not securely erase an incident reference that was derived from them.

Diagnosis is generated from incident evidence and is not stored separately. Text and JSON diagnosis output include service identity, evidence identifiers, typed facts, timestamps, relationships, history identifiers, and limitations. They exclude evidence summaries and raw journal/process content, but the remaining operational metadata may still be sensitive when copied or shared.

Incident inspection applies the same boundary. List output includes incident identity, lifecycle, service identity, and lifecycle timestamps. Detail output adds structured evidence identifiers, facts, relationships, quality limitations, and the existing diagnosis, but never evidence summaries, raw journal bodies, process commands, or executable paths. Inspection is generated locally and is not persisted. Incident IDs, unit names, cursors, process lifetime identifiers, and timestamps are still sensitive operational metadata; operators should review output before sharing it.

Continuous runtime output is intentionally narrower than stored observations. It exposes collector and journal statuses, observation/event counts, snapshot identity, incident candidate/reconciliation identities, timing, and generated limitation codes. It does not serialize snapshot objects, journal events, raw warnings or error messages, commands, executable paths, environment variables, or evidence summaries. The runtime necessarily passes bounded journal events transiently to existing correlation code, then retains no event batch. Local snapshot and event tables continue to contain the previously documented operational data and remain protected by owner-only database permissions rather than encryption.

Runtime ownership uses an empty adjacent file with mode `0600`. No PID, hostname, command, token, or database content is written to it. The one-cycle in-memory temporal baseline strips process commands and executable paths and discards unrelated observations and collector diagnostics. Durable snapshot/event privacy remains unchanged: the database still contains the bounded operational source data described above.
