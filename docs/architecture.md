# Sentinel architecture

Sentinel is deliberately local-first and read-only. Linux access is isolated in collectors; immutable models perform no I/O; the application service composes collector results; and the CLI formats application output only.

Every collector returns a `CollectionResult`. `success`, `partial`, `permission_denied`, `unsupported`, `transient_failure`, and `invalid_data` are distinct states. An unavailable process or service list is never represented as a successful empty list.

Phase 2 adds a versioned SQLite memory foundation. Schema migrations are explicit and transactional; queryable snapshot children use foreign keys with cascading deletion. Timestamps use UTC, process history uses PID plus `start_time_ticks`, and raw CPU/network counters remain authoritative. Observations are relational columns rather than a monolithic snapshot JSON blob.

Phase 3 adds a reusable foreground sampler. It starts one collection/persistence operation immediately, then advances monotonic deadlines by the configured interval (60 seconds by default). Work duration does not accumulate normal drift. An overrun skips missed deadlines instead of creating queued or overlapping samples. `request_stop()` prevents the next iteration and interrupts the normal wait; an in-progress synchronous sample is allowed to finish. Collector quality remains part of each stored snapshot. Persistence and unexpected errors propagate to the caller, while the sampler performs no health analysis or notification.

Phase 4 adds pure temporal comparison over two existing snapshots. The caller supplies the actual elapsed monotonic duration; wall-clock snapshot timestamps are deliberately not used to calculate rates. Raw counters remain authoritative. CPU comparison derives aggregate tick deltas, tick rates, and utilization only when all counters are continuous. Network byte counters are matched by interface, and process CPU counters only by `pid:start_time_ticks`; resets, missing values, first observations, new/removed resources, and PID reuse remain explicit non-rate states. The layer persists no derived values and makes no health judgement.

Phase 5 derives process lifecycle facts from two `SnapshotCollection` values without adding redundant storage. It matches process lifetime identity in O(N), provides continuing-process CPU-counter rate plus RSS and virtual-memory deltas, and keeps counter resets or invalid intervals explicit. New, exited, identity-changed, invalid, and insufficient-history processes remain distinct. A partial or failed process collection never generates inferred exits; exits require complete observations on both sides. This is temporal evidence only, not scoring, diagnosis, or alerting.

Phase 6 extends existing service comparison and journal storage. Services are matched by canonical unit name in O(N); unchanged, changed, new, removed, invalid, and insufficient-history observations are explicit. Incomplete inventories cannot establish additions/removals. Service snapshots preserve load, active, and sub-state for later analysis; a PID is not service identity, and sampled states cannot establish a restart count.

Journal events use the authoritative cursor as identity and preserve boot context where supplied. `JournalEventService` collects outside a database write transaction, then stores events, the checkpoint, and latest collection quality atomically. A conditional checkpoint check rejects competing stale writers. Failed polls preserve the last accepted cursor; invalidated cursors require explicit operator recovery and never silently restart at a new point. Models own the event/batch contracts; collectors do not write SQLite and storage does not import collectors.

Schema v2 provides event records and source checkpoints. The forward migration to v3 adds event warnings and latest collection quality and normalizes legacy event timestamps for correct ordering. Existing snapshot/service tables are reused. Bounded reads and batched writes use the same connection and transaction infrastructure. The retention module caps event rows on writes (10,000 by default) and provides manual time-based deletion; snapshot deletion and event deletion remain independent. Neither retention path deletes the checkpoint.

The existing foreground sampler can invoke any recorder with `record()`, including the explicit event service. Automatic combined scheduling, daemon packaging, anomaly scoring, diagnosis, root-cause correlation, alerting, notifications, AI agents, and remediation remain outside Phase 6. No type checker or new CI pipeline is added, and passing runtime tests is not a claim of complete static type verification.

Phase 7 preserves four distinct layers: an observation is a collected Linux fact; temporal interpretation describes a change between identified observations; evidence is a bounded reference to one authoritative fact plus the explicit relationship used; an incident candidate is durable derived state formed from at least two evidence kinds. Correlation is not diagnosis and does not claim that temporal proximity proves causality.

The initial deterministic rule anchors an incident on a canonical service transition into `failed`, `inactive`, or `deactivating`, or on a confirmed removal. A journal event relates only when its exact systemd unit matches and its UTC timestamp is inside the inclusive configured window. A process change relates only through a caller-supplied association to the exact `pid:start_time_ticks` lifetime; Sentinel currently has no collector that establishes systemd process ownership, so names, executable paths, event PIDs, and PIDs alone never create that association. System-wide resource changes are not correlated in this phase.

The incident ID is a versioned SHA-256 digest of the rule, service identity, and immutable opening service evidence. Reprocessing the same opening fact is idempotent; a later opening transition has a different identity. SQLite schema v4 stores the candidate, structured evidence references, and quality limitations in normalized tables. Reconciliation is transactional, preserves one opening anchor, bounds evidence at 128 references, and resolves only after an authoritative complete service sample contains an explicit transition back to active. Missing, partial, or failed collections never establish resolution.

Correlation inputs default to 10,000 facts per category with a hard configurable ceiling of 100,000, and each candidate defaults to 32 evidence references. Unit/time event lookup uses the existing event index, reads `limit + 1`, and reports truncation explicitly. Queries and output ordering are deterministic. Incidents do not copy journal messages or process commands. Resolved-incident retention is explicit; source snapshot/event retention remains independent, so an old evidence reference may outlive its authoritative source fact.

Diagnosis, causal/root-cause inference, anomaly detection, process ownership discovery, alerting, notifications, AI-assisted interpretation, remediation, and production daemon packaging remain future work.

Phase 8 adds deterministic diagnosis as another derived layer. A diagnosis consumes one bounded incident and its typed evidence facts; it neither rereads Linux nor replaces incident evidence. Schema v5 adds a structured `fact` field to evidence because prose summaries cannot safely establish whether an associated process exited, started, or changed identity. Existing schema-v4 evidence migrates to `unknown` and is never reinterpreted by parsing its summary. Reprocessing may enrich an unknown legacy fact while semantic conflicts remain errors.

Rules are ordered from strongest to weakest: failed service with exact-unit journal evidence and an explicitly associated process termination; failed service with exact-unit journal evidence; failed service with associated process termination; insufficient evidence; and unknown/unsupported opening condition. Explanations state co-occurrence and the exact relationship. Every result says that causal direction and root cause are not established. Partial, denied, unavailable, invalid, cursor-continuity, event, and incident limitations propagate into the explanation.

Diagnosis is regenerated deterministically from stable incident state, so it has no duplicate persistence table or retention policy. Up to 20 earlier candidates for the exact service identity may be mentioned as historical context; history does not imply a recurring cause. The `diagnose` CLI exposes bounded structured provenance and never includes raw journal messages, process commands, or executable paths.

Sentinel still does not discover systemd process ownership, infer system-wide resource causes, score confidence, diagnose arbitrary Linux failures, alert, notify, remediate, invoke AI/ML, or run as a production daemon.

Phase 9 adds an inspection layer over persisted incidents and derived diagnoses. `IncidentInspectionService` reuses the bounded `IncidentRepository` reads and `DiagnosisService`; it does not collect Linux state, recompute lifecycle, persist a view, or define new diagnostic rules. The plural CLI lists remembered incidents newest-first using the repository's explicit `(last_observed_at DESC, incident_id ASC)` ordering, a default limit of 100, and a hard maximum of 1,000. Optional lifecycle filtering uses the stored `active` or `resolved` state exactly as recorded.

Single-incident inspection combines the existing candidate and diagnosis contracts. Evidence remains ordered by timestamp, kind, and identity. Structured facts distinguish established values from legacy `unknown` references, while diagnosis and evidence limitations remain separate and visible. An active candidate is historical lifecycle state rather than a claim that the service is currently failing; resolution is shown only when the authoritative Phase 7 transition was stored. The versioned inspection JSON and text formatter share explicit serializers, and the embedded diagnosis uses the dedicated diagnosis serializer so the two commands cannot silently diverge.

Inspection output deliberately omits evidence summaries, journal bodies, process commands, and executable paths. It adds no database schema, history table, collector, causal inference, severity, current-state lookup, alerting, or remediation.

Phase 10 adds a narrow foreground runtime. `ContinuousObservationRuntime` is a recorder driven by the existing `Sampler`, so scheduling retains monotonic deadlines, skipped overruns, non-overlap, interruptible waits, and visible unexpected failures. Each cycle persists one quality-preserving snapshot, advances the existing bounded journal checkpoint service, derives process and service facts from only the prior completed in-memory collection, queries bounded exact-unit event windows, and delegates reconciliation to `IncidentFormationService`. It supplies no process/service association because no authoritative ownership source exists.

The runtime keeps only the previous completed `SnapshotCollection`, its monotonic observation point, and a cycle counter. It streams each immutable `RuntimeCycle` through a caller-provided sink instead of retaining an unbounded result history. On restart the first cycle is deliberately a new temporal baseline: it cannot infer exits, removals, transitions, or recovery from persisted wall-clock timestamps. The journal cursor and stored event facts do survive restart, and current failure transitions can correlate with exact-unit events ingested by an earlier cycle.

Snapshot, journal, and incident writes retain their existing independent transactions; Phase 10 does not claim whole-cycle atomicity. A later-stage failure remains visible and already committed earlier stages remain valid. Runtime state advances only after incident reconciliation succeeds, allowing an in-process retry to compare against the prior completed baseline. Expected collector failures continue as quality states, while SQLite, invariant, and programming errors abort the run.

Runtime bounds cover intervals (0.1 seconds through one day), finite cycle counts (up to 100,000), journal polls (up to 1,000), persisted correlation event reads, incident inputs/evidence, process observations (10,000 by default), and snapshot retention (10,000 by default). Process truncation is deterministic and marks the inventory partial, so omitted processes cannot become false exits. Snapshot trimming occurs in the same transaction as each runtime snapshot write. Cycle output contains only counts, statuses, timestamps, generated limitation codes, and incident identities.

Phase 11 gives each complete `ContinuousObservationRuntime.run()` an adjacent, owner-only runtime lease. It uses Linux `flock` with non-blocking exclusive ownership and retains the close-on-exec descriptor for the entire sampling run, including waits. A second runtime for the canonically resolved database path fails immediately; ordinary database readers do not take this lease. Closing the descriptor releases ownership on normal shutdown, exceptions, or signals, and the kernel releases it after an unclean process exit. The empty lock file deliberately remains because file existence is not ownership and no stale-file deletion race is needed.

The lease does not replace SQLite transactions. Snapshot, journal, and incident writes remain separate, explicit transactions with rollback local to the failed stage. WAL permits concurrent readers, the five-second SQLite busy timeout bounds persistent write contention, and lock/corruption exceptions remain visible. A crash can therefore leave earlier stages durable without claiming a whole-cycle commit. Journal checkpoints and incidents survive; the in-memory monotonic baseline never does.

The retained temporal baseline is now narrower than a persisted snapshot: it contains only service observations, sanitized process facts, source status/timestamps, and no commands, executable paths, unrelated system observations, warnings, error messages, or duration diagnostics. It is replaced only after snapshot, journal, event-query, correlation, and incident stages complete. Restart still begins with insufficient history, so it cannot manufacture exits, removals, state transitions, or resolution.

`sentinel run` remains a foreground process rather than a daemon or service installer. SIGINT and SIGTERM request a graceful stop and allow the active synchronous cycle to finish. Multiple concurrent `run` processes are not coordinated by a global runtime lease; SQLite and journal checkpoint conflict safeguards still apply, but operators should run one instance per database.
